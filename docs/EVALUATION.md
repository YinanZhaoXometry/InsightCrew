# InsightCrew evaluation

What has been measured, how to reproduce it, and what each result does and does not show.

Results marked **re-run** were reproduced on 2026-11-18 on Python 3.15.2 (macOS) in offline mode. Results marked **archived** come from a result file committed to the repository and were not re-run, because no API key was available.

Run all commands from the `InsightCrew/` directory.

## Dataset

`data/orders.csv` (1,200 orders) and `data/refunds.csv` (166 refunds) are synthetic, generated by `data/make_data.py` with `random.seed(42)`. They cover 2026-06-01 to 2026-10-14, three regions and three sales channels.

The traps are built in at known rates: 18.2% of orders are cancelled, 55.9% use a coupon, and 13.8% have a refund.

Synthetic data was chosen for three reasons. The correct answer is fixed by the metric dictionary, so "the audit works" can be tested rather than asserted. Each trap can be injected and checked separately. And every number in this document can be reproduced on another machine.

The cost is realism. Real data has duplicate rows, late refunds, currency and tax issues, none of which are present.

## What each experiment shows

### Error injection

For each of the 10 answerable questions, the real Critic is given five candidate answers: one correct, one with the right plan and a value inflated by 13%, and three where one required rule is switched off and the value is computed correctly under that wrong rule.

| Injected case | Expected | Rejected | Layer that caught it |
|---|---|---|---|
| Correct answer | PASS | 0 of 10 (no false alarms) | n/a |
| Value inflated 13% | REVISE | 10 of 10 | L2 |
| Refunds not subtracted | REVISE | 10 of 10 | L3 |
| Coupons not subtracted | REVISE | 10 of 10 | L3 |
| Cancelled orders included | REVISE | 10 of 10 | L3 |

In the 30 rule cases, the SQL recomputation agrees with the wrong value, because both use the same wrong filters. Only the dictionary check rejects them. This is the evidence that L3 is necessary and not redundant with L2.

**Limits of this result.** It uses the revenue metric only. Five of the 10 questions share identical filters, so there are 6 distinct filter sets, not 10. And it tests the Critic against errors of a known shape: it does not show the Critic catches errors nobody anticipated.

### Offline ablation

| Mode | What is removed | Correct | Average rounds |
|---|---|---|---|
| `full` | Nothing | 12 of 12 | 1.67 |
| `no_critic` | Critic always returns PASS | 2 of 12 | 0.83 |
| `single` | No profile, a one-line plan with no filters, Critic always returns PASS | 2 of 12 | 0.83 |

The two questions that the reduced modes still get right are the unanswerable ones, which the scope gate declines before any agent runs.

**Limits of this result.** In offline mode the scripted model's first attempt is wrong by design. So "2 of 12 without the Critic" is true by construction: it shows that nothing else in the pipeline catches a wrong first answer, not how often a real model gives one. For the same reason `single` and `no_critic` are indistinguishable offline. These numbers should be presented as a mechanism demonstration, not as a performance comparison.

### Real model

From `eval/result_online.json`, `deepseek-chat` at temperature 0:

| Outcome | Questions |
|---|---|
| Passed on the first round | 7 |
| Rejected once, then passed | 3 |
| Correctly declined before any model call | 2 |

The three rejections are the informative part:

| Question | First verdict | What happened |
|---|---|---|
| Company-wide average order value, Q3 | REVISE (L3) | The plan left a required rule off. The Planner re-planned. |
| East China refund rate, Q3 | REVISE (L2) | Plan compliant, value differed from SQL. The Analyst re-coded with the plan unchanged. |
| North China refund rate, September | REVISE (L2) | Same as above. |

So on this run the real model produced a wrong first answer for 3 of 10 answerable questions, and the audit loop recovered all three. Both feedback edges were exercised: one re-plan and two same-layer repairs.

**Limits of this result.** One run per question, one model, 12 questions. There is no variance estimate. No real-model run with the Critic disabled has been archived, so the natural claim "the audit raised accuracy from 7 of 10 to 10 of 10" is an inference from the verdict history, not a measured ablation. Running `python3 -m eval.run_eval --mode no_critic` with an API key would measure it directly and is the first item in the roadmap.

### Disabling L3 only

With the dictionary check forced to return no issues, the default question passes in one round with the value 1,189,734.57 and confidence "high": a 14.8% overstatement delivered as verified. Re-run on 2026-11-18 by replacing `MetricDict.required_issues` at run time.

To reproduce by hand, comment out the L3 block in `agents/critic.py`, run `python3 ask.py`, then restore the file with `git checkout agents/critic.py`.

### With and without the audit, one command

```bash
python3 ask.py "2026年第三季度华东区的营收是多少？" --compare
```

Prints 1,189,734.57 without the audit (1 round) and 1,036,538.28 with it (2 rounds): a difference of 153,196.29.

## Failure cases

These were found on 2026-11-18. All are reproducible in offline mode. None has been tested with a real model, whose Planner may handle some of them differently.

### 1. The wrong question answered with high confidence

The scope gate declines unknown metrics, regions, periods and channel breakdowns. It does not recognise other kinds of intent, and the Critic never compares the plan with the question. Each of these returned a number marked high confidence:

| Question | What was asked | What was answered |
|---|---|---|
| `What was the revenue of East China in Q3 2026?` | East China | Whole company, 3,031,580.71. The English region name was not recognised and was dropped. |
| `2026年上半年华东区的营收是多少？` | First half of 2026 | 2026-06-01 to 2026-10-14. "First half" was not parsed, so the period defaulted to the full year and was clipped to the data. |
| `2026年第三季度华东和华北哪个区营收更高？` | Which of two regions is higher | The sum of both regions, 2,031,310.39 |
| `2026年第三季度华东区营收环比增长了多少？` | Quarter-on-quarter growth | The Q3 revenue itself |
| `2026年第三季度华东区平均每天的订单量是多少？` | Orders per day | Total orders, 233 |
| `2026年第三季度华东区已取消订单的订单量是多少？` | Count of cancelled orders | Count of non-cancelled orders, 233 |

This is the most important limitation. The system's central claim is that it declines rather than answer wrongly, and these cases fall outside that guarantee. The audit proves "this number follows from this plan under the dictionary". It does not prove "this plan is what the user asked".

### 2. A rejected value shown as the conclusion

With `IC_MAX_TURNS=1`, the default question ends after the first rejection. The report's conclusion line reads `营收 = 1,189,734.57 CNY`, the value the Critic had just rejected. It is marked low confidence and the unresolved issues are listed below it, but a reader who looks only at the headline gets the wrong number.

### 3. Sandbox bypass

These pass the static check: `open('/etc/hosts').read()`, `open('x.txt', 'w')`, `getattr(__builtins__, '__imp' + 'ort__')('os')`, and walking `().__class__.__bases__[0].__subclasses__()`. Checked against `sandbox.static_check` only; none was executed.

The environment is not inherited, so the API key is not readable from `os.environ`. A `.env` file on disk is readable by absolute path.

### 4. Mixed traces in batch runs

The run directory name has one-second resolution. Runs that start in the same second share a directory: `trace.jsonl` is appended to and `blackboard.json` is overwritten. After `eval.run_eval`, one directory held 24 runs' events and one blackboard. `ask.py --compare` in offline mode is affected too. Single interactive runs are not.

### 5. A failed first model call crashes the run

With a real-model configuration pointing at an unreachable endpoint, `Orchestrator.run()` raises `RuntimeError` from the Profiler call. No report and no `blackboard.json` are written. Failures in later calls are converted to a degraded report as intended. In a live demo, a network failure at the start would show a traceback.

### 6. The dictionary decides

Remove `subtract_refund` from the revenue entry in `data/metric_dict.json` and the system stops requiring refunds to be subtracted. The audit is as reliable as the dictionary, and the dictionary is written by hand.

## Threats to validity

- **Small, overlapping question set.** Five of the 12 questions are the same computation phrased differently.
- **One model, one run.** No repeated runs, no second model.
- **Synthetic data with anticipated traps.** No order has more than one refund, so the double-counting risk the Profiler warns about is never exercised.
- **Reference answers share code with the Critic.** `eval/questions.jsonl` expected values come from the same SQL path the Critic uses. `eval/online_eval.py` adds a third, separately written computation (it reuses only the question parser), and the archived run matched it on all 10 answerable questions.
- **The Profiler's contribution is not isolated.** No experiment removes only the Profiler.
- **Date dependence.** Relative periods such as "last quarter" resolve against today's date. The archived online result for that question is valid for runs dated October to December 2026.

## Side effects of the evaluation scripts

- `eval.inject_test` rewrites the tracked file `eval/result_inject.json`. On macOS or Linux this changes every line ending and shows as a 1,160-line diff with no change in content. Restore it with `git checkout -- eval/result_inject.json`.
- `eval.run_eval` writes a new `eval/result_<mode>_<timestamp>.json` on every run.
- `eval.online_eval` overwrites `eval/result_online.json`. Keep a copy of the archived file before re-running.
- Every run adds a directory under `runs/`, which is ignored by git.
