# COMP5584 小组项目设计方案

## InsightCrew：带验证回路的多智能体数据分析助手
### （InsightCrew: A Multi-Agent Data Analysis Assistant with Verification Loop）

> 本文档用于：① 开题/分工讨论 ② 幻灯片前三页的素材 ③ 代码实现的规格说明书。
> 场景对应指南中的 "Data analysis" 方向，但真正的得分点不在场景，而在**验证回路（reflection & verification）**这一协作机制。

---

## 0. 一句话立项

> 用户用自然语言提出一个数据分析问题，系统由 5 个角色分工的智能体协作，在**结构化的业务数据**（订单表 + 退款表，演示用合成数据集，固定随机种子可复现）上自动产出一份含图表、结论与可信度标注的分析报告；其中 **Critic 智能体会独立复算关键数字并驳回错误结论**，被驳回后由 Planner 重新规划、Analyst 重跑代码。

**为什么这个题目容易得高分**（对照 rubric）：

| 评分项 | 本方案如何命中 |
|---|---|
| 问题建模 15% | 传统单 agent 做数据分析有三个硬伤：口径错、算错、结论过度外推。三者恰好需要**三种不同视角**才能互相制衡 |
| 系统设计 30% | 5 个角色职责正交；共享黑板（blackboard）+ 结构化消息协议；Supervisor 负责路由与预算；存在显式的**质疑—驳回—重跑**回路 |
| 技术实现 25% | 工具体系明确（Python 沙箱 / SQL / 画图 / 指标字典 RAG）；可一键复现；错误可观测（消息日志） |
| 分析创新 15% | 天然可做对照实验：Single-Agent vs Multi-Agent 的数字准确率；Critic 驳回率；失败案例可复现 |
| 展示 15% | 演示有"剧情"：先算错 → Critic 抓到 → 自我修正 → 出正确报告，视频很好看 |

## 1. 系统架构

### 1.1 角色表（这是 rubric 第 2 项的核心，务必逐列填满）

| # | Agent | 角色 | Goal（目标） | 可用工具/信息 | 输入 | 输出 |
|---|---|---|---|---|---|---|
| 1 | **Supervisor**（监督者/调度） | 路由器 + 预算控制 + 终止判定 | 判断当前状态该由谁行动，控制轮数上限 | 全局黑板、历史消息、轮次预算 | 用户问题 + 黑板状态 | 下一条指令（给某个 agent 的 task 消息） |
| 2 | **Profiler**（数据画像） | 数据理解专家 | 弄清数据结构、字段含义、缺失与异常 | `read_schema`、`sample_rows`、`describe`、指标字典检索 | 数据表 + 用户问题 | 数据画像卡（JSON：字段/类型/口径/坑点） |
| 3 | **Planner**（规划者） | 分析方案设计 | 把自然语言问题拆成可执行的子问题与步骤 | 数据画像卡、历史失败记录 | 画像卡 + 问题 | 分析计划（步骤 DAG + 每步预期产出） |
| 4 | **Analyst**（执行者） | 代码执行 + 初步结论 | 按计划写 Python/SQL 并执行，产出中间结果 | **Python 沙箱**（pandas/sqlite）、绘图工具 | 分析计划 + 数据 | 代码 + 执行结果 + 草稿结论（含引用的数字） |
| 5 | **Critic**（验证者） | 独立审计 | 复算关键数字、检查口径与逻辑、判断结论是否被数据支持 | `recompute`（独立实现一遍计算）、原始数据、指标字典 | 草稿结论 + 代码 + 中间结果 | 判定：`PASS` / `REVISE`（附具体问题定位与修改建议） |
| 6 | **Reporter**（撰写者） | 报告生成 | 把已验证的结论写成结构化报告与图表 | 图表工具、模板 | 通过审核的结论 | Markdown/HTML 报告（结论 + 图 + 数据出处 + 置信度） |

> 最少可实现版本（MVP，工期紧时）：**Planner + Analyst + Critic** 三角，Supervisor 用代码里的 while 循环代替，Reporter 用模板字符串代替。三角就已经满足"角色正交 + 验证回路"的得分点。

### 1.2 协作流程图

```
            用户问题
               │
        ┌──────▼───────┐
        │  Supervisor  │◄──────────────┐
        └──────┬───────┘               │ 每轮重新路由
               │ task                  │
   ┌───────────┼───────────┬───────────┴──────┐
   ▼           ▼           ▼                  │
Profiler   Planner     Analyst ──► Critic ────┘
   │           │           ▲         │
   │ 画像卡     │ 计划       │ 重跑     │ REVISE（附问题定位）
   └──────────►└──────────►│         │
                           └─────────┘
                                      │ PASS
                                      ▼
                                  Reporter ──► 报告
```

### 1.3 通信机制（指南要求"如何通信"，要有具体协议，别只说"它们会对话"）

- **共享黑板（shared workspace）**：一个 `Blackboard` 对象，含 `question`、`profile`、`plan`、`artifacts[]`（代码+输出）、`critiques[]`、`report`、`turn_count`。所有 agent 读写同一份，是**唯一的真相来源**。
- **结构化消息**（不用自由文本传递任务，避免语义漂移）：

```json
{
  "msg_id": "m_012",
  "from": "Supervisor",
  "to": "Analyst",
  "intent": "EXECUTE_STEP",
  "payload": {"step_id": 3, "instruction": "按季度汇总营收，注意剔除退款单", "expected_output": "表格"},
  "constraints": {"max_tokens": 800, "must_use_tools": ["python"]},
  "refs": ["artifact_a2"]
}
```

- **终止条件**（必须有，否则演示会跑飞）：Critic 返回 `PASS` → 进入 Reporter；或 `turn_count >= 12`；或连续 2 次 REVISE 同一问题 → 降级输出"部分结论 + 未解决项"。

### 1.4 工具集

| 工具 | 谁用 | 作用 |
|---|---|---|
| `python_sandbox` | Analyst | 沙箱内执行 pandas 代码，返回 stdout + 异常栈（异常栈回传给 Critic 作为证据） |
| `sql_query` | Analyst | 结构化表查询 |
| `chart_gen` | Analyst/Reporter | matplotlib/plotly 出图 |
| `metric_dict_search` | Profiler/Critic | RAG 检索"指标口径字典"（如"营收是否含税""活跃用户定义"），**这是 Critic 判断口径错误的依据** |
| `recompute` | Critic | 用**不同实现路径**复算同一指标（如 Analyst 用 groupby，Critic 用 SQL），比对结果 |
| `log_trace` | 全体 | 全链路消息日志，供演示与分析 |

> 设计要点：Critic **不能看 Analyst 的推理过程，只能看代码 + 数据 + 结论**。这叫"独立复算"，是让验证真正有效、而不是自我确认的关键。

## 2. 为什么必须多智能体（15% 分就在这段话里）

单 agent 做数据分析的失败模式是**结构性的**，不是"模型不够强"：

1. **自我确认偏差**：同一个上下文里生成的结论，再让它自己检查，它倾向于沿用已有推理路径，重复同一个错误（尤其是口径错、单位错）。
2. **上下文污染**：数据画像（几百行 schema）、分析计划、几轮代码报错全部挤在一个上下文里，后期推理质量下降。
3. **目标冲突**：执行者追求"跑通"，审计者追求"可信"，这两种倾向在同一个 prompt 里会互相稀释。

多智能体带来的四个可测量收益：

| 收益 | 可测指标 |
|---|---|
| 独立验证 | Critic 驳回率、驳回后修正成功率 |
| 上下文隔离 | 每个 agent 的 prompt 长度、长任务下的准确率下降幅度 |
| 职责专精 | 各 agent 的 prompt 与工具集明显不同（可在 slides 里展示对比） |
| 可审计 | 每一步都有结构化日志，错误可定位到具体 step |

## 3. 技术栈建议

| 层 | 选型 | 理由 |
|---|---|---|
| 模型 | 任一 OpenAI 兼容 API（DeepSeek / Qwen / GPT-4o-mini 均可） | 便宜、可换；**不要锁死某一家**，答辩时可讲"模型可插拔" |
| 编排 | **自己写 200 行编排器** > LangGraph/CrewAI | 自研更能讲清机制，且避免"框架黑箱"被质疑；若时间紧可用 LangGraph 但必须能讲清它的状态机 |
| 执行 | `subprocess` + 受限 `exec`（禁 `os`/`open` 写）或 Docker | 安全 + 可讲"沙箱设计" |
| 记忆 | 短期=黑板（内存/JSON 落盘）；长期=`data/lessons.jsonl` 失败经验库 | 体现"经验复用"这个加分点 |
| 前端 | Streamlit / Gradio / 简易 FastAPI + 静态页 | 需要能**实时看到 5 个 agent 的消息流**，这是演示的灵魂 |
| 数据 | 自带 2~3 个 CSV（销售流水 / 学生成绩 / 传感器日志） | 确定性数据 = 可复现 = 可自动评分 |

## 4. 对照实验设计（15% 分析分的关键）

跑同一批 20 个问题，两种配置：

| 配置 | 说明 |
|---|---|
| Baseline-Single | 一个 agent + 同样工具，一次生成报告 |
| Ours-Multi | 本方案 5 角色 + 验证回路 |

统计：**数字正确率**（人工标注答案）、**口径错误数**、**平均轮数**、**token 成本**、**平均耗时**。

预期结论（也正是论文里常见的发现）：多 agent 在**数字正确率**上提升显著，但**成本翻倍** —— 诚实报告这个 trade-off 本身就是加分项（rubric 明确要求讨论 limitations）。

| 时间 | 内容 |
|---|---|
| 0:00–1:00 | 问题与动机：单 agent 分析报表"看起来很对但数字是错的"的真实例子 |

## 8. 常见扣分点（自查清单）

- [ ] 只是 prompt 里写"你是分析师/你是审核员"，但**信息流没有真正隔离**（Critic 读到了 Analyst 的思考过程）→ 会被判为"伪多智能体"
- [ ] 没有终止条件，靠"感觉跑完了"
- [ ] 演示用的是 toy 数据 + 编好的答案，没有真实计算
- [ ] 没有失败案例（rubric 明确要求 limitations & failure cases）
- [ ] 视频超 10 分钟
- [ ] 贡献声明写得像模板，与实际代码提交记录不符
